## 1. Предметная область

Сервис доставки продуктов «Самокат» — система экспресс-доставки (за 15 минут), в которой клиенты, сборщики, курьеры и администраторы взаимодействуют в рамках обработки заказов.

**Основные сущности:**
- **Пользователь (User)** — клиент, курьер или сборщик с ФИО, телефоном и ролью (customer, courier, picker, admin)
- **Товар (Product)** — продукт из каталога с названием, ценой и остатком на складе (stock)
- **Заказ (Order)** — оформленный клиентом заказ с суммой, статусом и временем создания
- **Позиция заказа (OrderItem)** — конкретный товар и его количество в рамках заказа
- **Даркстор (Darkstore)** — склад, к которому привязан клиент и с которого собирается заказ
- **Платеж (Payment)** — транзакция холдирования и списания средств

**Ключевые процессы:**
- Просмотр клиентом каталога товаров и поиск
- Оформление заказа и онлайн-оплата (холдирование средств)
- Передача заказа на сборку в даркстор
- Сборка заказа сборщиком и передача курьеру
- Доставка курьером и финализация оплаты
- Отслеживание статуса заказа в реальном времени

## 2. Матрица стейкхолдеров и прав доступа (Ролевая модель)

| Функция системы | Клиент | Сборщик | Курьер | Администратор | Система Даркстора |
|---|---|---|---|---|---|
| Просмотр каталога и поиск товаров | Да | Нет | Нет | Да | Нет |
| Управление корзиной и промокодами | Да | Нет | Нет | Нет | Нет |
| Оформление и оплата заказа | Да | Нет | Нет | Нет | Нет |
| Отслеживание статуса и таймера | Да | Нет | Нет | Да | Нет |
| Просмотр листа сборки | Нет | Да | Нет | Нет | Да |
| Отметка «Сборка завершена» | Нет | Да | Нет | Нет | Нет |
| Просмотр готовых к выдаче заказов | Нет | Нет | Да | Нет | Нет |
| Отметка «Взял заказ» / «Доставлено» | Нет | Нет | Да | Нет | Нет |
| Списание остатков со склада | Нет | Нет | Нет | Нет | Да |
| Управление пользователями и ролями | Нет | Нет | Нет | Да | Нет |

**Архитектурное противоречие:** Клиенту необходима мгновенная загрузка каталога и быстрая оплата, а системе даркстора и аналитике — тяжелые операции по списанию остатков и расчету загрузки курьеров. Если генерировать тяжелые отчеты и блокировки склада в той же БД, где клиент оформляет заказ, приложение упадет в час пик (вечером).

**Решение (CQRS):** разделить систему на два контура:
- **Транзакционный (OLTP)** — быстрые операции: оформление заказа, оплата, смена статусов.
- **Аналитический (OLAP)** — отдельное хранилище для отчетов по продажам и загрузке курьеров, синхронизация через очередь сообщений (Kafka).

## 3. Функциональные требования (FR)

### Модуль А: Каталог и корзина (Catalog & Cart Module)

- **FR-01 (Управление каталогом):** Система должна предоставлять интерфейс для просмотра товаров с указанием названия, цены и остатка на складе.
- **FR-02 (Управление корзиной):** Система должна позволять Клиенту добавлять товары в корзину и изменять их количество.
- **FR-03 (Применение промокодов):** Система должна валидировать промокод на сервере и пересчитывать итоговую сумму заказа.
- **FR-04 (Проверка зоны доставки):** Система должна автоматически определять, входит ли адрес клиента в зону обслуживания, и привязывать его к ближайшему даркстору.

### Модуль Б: Заказы и платежи (Order & Payment Engine)

- **FR-05 (Оформление заказа):** Система должна создавать заказ со статусом `CREATED` и резервировать товары на складе.
- **FR-06 (Онлайн-оплата):** Система должна интегрироваться с платежным шлюзом для холдирования средств и подтверждения оплаты.
- **FR-07 (Защита от двойных заказов — Race Conditions):** Система должна гарантировать, что при повторном нажатии кнопки «Оплатить» деньги не спишутся дважды (идемпотентность платежей).
- **FR-08 (Финализация оплаты):** Система должна отправлять команду в платежный шлюз на окончательное списание средств (Capture) только после успешной доставки.

### Модуль В: Логистика и исполнение (Logistics Module)

- **FR-09 (Передача на сборку):** После успешной оплаты Система должна менять статус на `ASSEMBLING` и выводить заказ на терминал Сборщика.
- **FR-10 (Передача курьеру):** Система должна позволять Курьеру принимать заказ (статус `IN_DELIVERY`) и отправлять клиенту push-уведомление с таймером.
- **FR-11 (Завершение заказа):** Система должна менять статус на `COMPLETED` после нажатия курьером кнопки «Доставлено» и инициировать списание денег.

## 4. Нефункциональные требования (NFR) на базе ISO 25010

**Бизнес-контекст:** «В вечерний час пик (18:00–20:00) тысячи пользователей одновременно открывают приложение, чтобы заказать продукты».

| Категория ISO 25010 | Контекст предметной области | Инженерная формулировка требования (NFR) |
|---|---|---|
| **Performance Efficiency** | Тысячи клиентов заходят в приложение одновременно после работы | **NFR-01:** Система должна выдерживать пиковую нагрузку не менее **3000 RPS** на эндпоинт получения каталога и не менее **500 RPS** на эндпоинт создания заказа при времени отклика (Latency) p95 не более **150 мс**. |
| **Reliability** | Сбой системы ведет к потере заказов и финансовым потерям | **NFR-02:** Архитектура должна исключать единую точку отказа (SPOF). Коэффициент доступности (Availability) ядра заказов должен составлять **99.95%** (SLA). |
| **Usability** | Клиент оформляет заказ на ходу со смартфона в плохой сети | **NFR-03:** Размер передаваемой по сети страницы каталога для мобильных устройств не должен превышать **250 Кб** в сжатом виде (gzip/brotli). |
| **Maintainability** | Правила наценок и промокодов могут меняться каждый день | **NFR-04:** Модуль расчета скидок и промокодов должен быть изолирован от логики корзины через паттерн «Стратегия» и покрыт unit-тестами минимум на **80%**. |
| **Security** | Риск DDoS-атак и ботов, скупающих товары по акции | **NFR-05:** Система должна иметь встроенный механизм Rate Limiting на уровне API Gateway, ограничивающий запросы с одного IP-адреса (не более **20 запросов в минуту**). |

## 5. Системные ограничения и допущения (Constraints)

Формализуем бизнес-рамки первой версии продукта (v1.0), которые нельзя нарушать архитектурно.

- **Constraint-01 (Ограничение по часовому поясу):** Система проектируется в расчете на работу в пределах одной временной зоны (Москва/MSK). Мультитаймзоновые расписания работы дарксторов не поддерживаются.
- **Constraint-02 (Ограничение по типам оплаты):** В v1.0 поддерживается только оплата банковской картой. Оплата наличными или через СБП не реализуется.
- **Constraint-03 (Технологический стек):** В качестве основного хранилища данных (заказов, пользователей) должна использоваться реляционная СУБД (например, PostgreSQL) с поддержкой транзакций для исключения аномалий конкурентного доступа при списании остатков.
- **Constraint-04 (Архитектурный стиль):** Система проектируется как набор независимых микросервисов с единой точкой входа через API Gateway (паттерн Backend-for-Frontend).
- **Constraint-05 (Ограничение по авторизации):** В v1.0 используется упрощенная авторизация по номеру телефона (без сложных OAuth 2.0 сценариев). Разграничение прав обеспечивается на уровне ролей.
- **Constraint-06 (Ограничение по интеграции с 1С):** Автоматическая синхронизация с 1С:Склад в v1.0 не реализуется — данные об остатках обновляются через API Даркстора.

## 6. Архитектура приложения (микросервисы)

| Сервис | Порт | Назначение |
|--------|------|-----------|
| `users_service` | 5001 | Управление пользователями (клиенты, курьеры, сборщики) |
| `products_service` | 5002 | Каталог товаров и остатки |
| `orders_service` | 5003 | Управление заказами и статусами |
| `api_gateway` | 8000 | Единая точка входа (FastAPI + httpx) |
| `web_app` | 5004 | Веб-интерфейс (Flask + Jinja2) |

**API Gateway** маршрутизирует запросы от Web App к микросервисам, обрабатывает ошибки (503 при недоступности сервиса) и предоставляет Swagger UI для документации.

## 7. Запуск проекта

```bash
# 1. Установка зависимостей
pip install -r requirements.txt

# 2. Запуск микросервисов (в отдельных терминалах)
cd users_service && python app.py        # порт 5001
cd products_service && python app.py     # порт 5002
cd orders_service && python app.py       # порт 5003

# 3. Запуск API Gateway
cd api_gateway
python -m uvicorn main:app --host 0.0.0.0 --port 8000 --reload

# 4. Запуск Web App
cd web_app && python app.py              # порт 5004
